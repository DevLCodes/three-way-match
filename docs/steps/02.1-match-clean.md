# Step 02.1: Rule matcher on a clean order

**Goal:** compare an order's invoice with its purchase order and receipt using fixed rules, and approve it only when nothing disagrees.

## Files

| File | What it is |
|---|---|
| [`src/three_way_match/match.py`](../../src/three_way_match/match.py) | `match(po, receipt, invoice)`, `product_key()`, and an entry point that prints the comparison |
| [`src/three_way_match/schemas.py`](../../src/three_way_match/schemas.py) | Adds `Exception_` (one reason not to approve) and `MatchResult` |
| [`tests/test_match.py`](../../tests/test_match.py) | Clean order approved, names matched ignoring case and spaces, 1-cent tolerance |

## Command

```bash
uv run python -m three_way_match.match 10250
```

## Output

```
product                                invoiced   ordered (PO)  received
Jack's New England Clam Chowder        10 @ 7.7       10 @ 7.7        10
Manjimup Dried Apples                 35 @ 42.4      35 @ 42.4        35
Louisiana Fiery Hot Pepper Sauce      15 @ 16.8      15 @ 16.8        15
invoice total                              1813   lines add up to 1813.0

{
  "order_id": "10250",
  "approved": true,
  "exceptions": []
}
```

Tests: `28 passed in 0.17s`. The documents came from the step 01.7 cache, so no LLM calls were made.

## What happened

"Three-way" means three questions, asked line by line about the invoice:

| Question | Compared with | Rule |
|---|---|---|
| Did we order this, at this quantity and price? | Purchase order | Quantity equal; unit price within 0.01 |
| Did it arrive? | Receipt | Invoiced quantity no more than received |
| Is the invoice's own arithmetic right? | The invoice itself | Sum of quantity × unit price within 0.01 of the printed total |

1. `match` builds a lookup of each document's lines by product. `product_key` lowercases names and squeezes spaces, so `"Chai "` and `"chai"` are the same product, but a different spelling is not: guessing at product names is how wrong invoices get paid.
2. For each invoice line it checks the PO, then the receipt. Every problem becomes an `Exception_` with a `code` (machine-readable, for the workflow), the `product`, and a `detail` (human-readable, for the approval screen).
3. It recalculates the total in code: 10 × 7.7 + 35 × 42.4 + 15 × 16.8 = 77 + 1484 + 252 = 1813.0, which equals the printed 1813.
4. `approved` is simply "no exceptions". There is no score and no LLM: the same documents always give the same answer, and every "no" comes with its reason.

The PO's customer name ("Mario Pontes", seen in step 01.7) differs from the invoice's, and the match still passes: the matcher compares what is bought and billed, not names. That check belongs to the fraud signals in Phase 6.

**The tolerance is 0.01** because prices printed with 2 decimals can be rounded differently on two documents. Anything more than a cent is a real difference.

**Why it matters next:** a clean order is the easy case. Step 02.2 breaks the documents on purpose to show every exception code firing.
