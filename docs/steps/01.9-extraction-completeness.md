# Step 01.9: Extraction completeness check

**Goal:** stop LLM extraction from silently dropping lines. Added after [step 02.2](02.2-exception-codes.md) found PO 11077 losing all 11 lines on its second page.

## Files

| File | What it is |
|---|---|
| [`src/three_way_match/completeness.py`](../../src/three_way_match/completeness.py) | `item_rows(text)`: counts item rows in the parsed LaTeX tables |
| [`src/three_way_match/extract.py`](../../src/three_way_match/extract.py) | After validation, fewer lines than `item_rows` counts is treated like invalid JSON: the gap goes back to the LLM; a second failure raises `IncompleteExtraction` |
| [`scripts/show_completeness.py`](../../scripts/show_completeness.py) | Counts rows for every document, re-extracts PO 11077, then forces a 14-line first answer to show the retry |
| [`tests/test_completeness.py`](../../tests/test_completeness.py) | Headers and totals not counted, continued tables counted, order-info tables ignored, retry and give-up |

## What happened

1. **Counting rows in code.** `item_rows` reads the LaTeX tables in the parsed text. A table counts as an item table if its header mentions products, quantities or prices; a table with *no* header that follows an item table is the same table continued on the next page (exactly PO 11077's page 2). Header rows and total rows are skipped. The order-info table (order id, date, customer) has no item words, so its row isn't counted. Receipts print items as `Product: … Quantity: …` text, not tables, so for them the count is `None` and the check stays out of the way.
2. **Wired into the existing retry.** `extract` already sent invalid JSON back to the LLM ([step 01.6](01.6-llm-extraction.md)). Now a valid but *short* answer is treated the same way: the feedback says how many lines came back, how many rows exist, and the likely reason (a headerless continued table). If the second answer is still short, `IncompleteExtraction` is raised; in the workflow that will send the case to investigation, not on to matching.
3. **Temperature 0 is not fully repeatable.** The same prompt on the same text gave 14 lines twice in step 02.2, then 25 lines on this step's first run, then 14 again on the second. Hosted models can vary between runs even at temperature 0. So the gap can't be fixed by trying until it works once: it needs a check that runs every time.
4. **The second run showed the real thing:** the model genuinely dropped page 2 on call 1, the check caught it, and call 2 returned all 25 lines. The forced run below it shows the same path deterministically.
5. **Order 11077 now has only its two true problems:** no receipt exists, and Nemotron dropped the invoice total. The 11 false "not on PO" exceptions are gone.

**Why the count comes from the parsed text, not the PDF text layer:** the parsed tables are exactly what the LLM was given, so a shortfall can only be the LLM's. Missing text in the parse itself is the step 01.8 cross-check's job. Together: text layer → parse is checked by 01.8, parse → extraction by 01.9.

**Why it matters next:** the reading pipeline now checks both of its AI steps in code. Phase 3 starts the database.
