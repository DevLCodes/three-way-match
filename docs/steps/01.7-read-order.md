## What happened

`read_order` loops over the three `DocType`s and, for each, runs the five stages from steps 01.1 to 01.6:

```
fetch_pdf -> render -> parse_page (per page) -> clean (per page) -> join pages -> extract -> cache
```

Times are cumulative per document. Reading the timings:

- **Fetch** was 0.6–0.7 s for the two new PDFs and 0.0 s for the invoice, which was already on disk from step 01.1.
- **Parse** took about 1.6–1.9 s per new page. The invoice page came from the parse cache (step 01.3), so 0.0 s.
- **Extract** is the slow part: 14–30 s per document, all of it LLM time. The whole order took 72 s.
- **Second run: 0.15 s.** `read_document` now saves each final `Document` to `data/extracted/<pdf name>.json`, so an order is only paid for once. The trade-off: if the prompt or model changes, delete `data/extracted/` to re-read.

**The receipt has 2 pages**, and its third product is split across them (product and quantity on page 1, price on page 2). Because the cleaned pages are joined into one text *before* extraction, the LLM sees the whole product and returns it as one line.

**Two things worth noticing in the results:**

1. **The PO's customer is "Mario Pontes", not "Hanari Carnes".** That is not a reading error: the PO itself says so (`10250 & 2016-07-08 & Mario Pontes` in its parsed table). The Northwind dataset is synthetic and its POs don't always agree with the other documents. The matcher (step 02.1) compares products, quantities and prices, not names, so this order still matches. A "PO for another party" check is a fraud signal in Phase 6.
2. **The PO total is `None`.** The PO doesn't print a total, and the prompt says never calculate one. The receipt total, 1813, is printed on its page 2.

All three agree on the products, quantities and prices, so order 10250 should match cleanly in the next step.
