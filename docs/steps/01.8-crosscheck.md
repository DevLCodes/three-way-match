# Step 01.8: Cross-check against the PDF text layer

**Goal:** catch the parser misreading or dropping a value, by comparing its output with the text the PDF itself carries.

## Files

| File | What it is |
|---|---|
| [`src/three_way_match/crosscheck.py`](../../src/three_way_match/crosscheck.py) | `text_layer(pdf)` and `missing_amounts(pdf, parsed_text)` |
| [`tests/test_crosscheck.py`](../../tests/test_crosscheck.py) | A dropped total is found, different spellings of one amount match, bare decimals checked, no text layer skips the check |

## Commands and output

First, a look at invoice 11077 (end of each text):

```
--- text layer p1: 1066 chars ---
...
Original Frankfurter grüne Soße $13.00 2 $26.00
Total: $1374.60
--- parsed invoice_11077_p1.png: 1427 chars ---
...
Original Frankfurter grüne Soße & \$13.00 & 2 & \$26.00\\
\mbox{} & \mbox{} & \multicolumn{2}{c}{\thead{Total:}}\\
\end{tabular}
```

The check, first version (amounts with a `$` only):

```
$ uv run python -m three_way_match.crosscheck receipt 10250
receipt 10250: 0 amounts in the text layer
  all found in the parsed text
```

0 amounts meant the receipt wasn't really checked: receipts print `7.7`, not `$7.70`. After widening the pattern to any decimal number:

```
$ uv run python -m three_way_match.crosscheck invoice 10250
invoice 10250: 7 amounts in the text layer
  all found in the parsed text
$ uv run python -m three_way_match.crosscheck invoice 11077
invoice 11077: 51 amounts in the text layer
  MISSING from parsed text: $1374.60
$ uv run python -m three_way_match.crosscheck receipt 10250
receipt 10250: 7 amounts in the text layer
  all found in the parsed text
$ uv run python -m three_way_match.crosscheck purchase_order 10250
purchase_order 10250: 3 amounts in the text layer
  all found in the parsed text
```

What extraction makes of 11077:

```
invoice: extracted 25 line(s) (58.0 s)
lines: 25 total: None lines add up to: 1374.60

$ uv run pytest -q
25 passed in 0.16s
```

## What happened

1. **Two copies of the same words.** A PDF made by software (not a scan) carries a *text layer*: the actual characters, used for copy-and-paste and search. `text_layer()` reads it with pdfium, no AI involved. Nemotron instead reads the *picture* of the page. Two independent reads of one page: if they disagree, one of them is wrong.
2. **Nemotron dropped the total on 11077.** Its table ends with an empty `Total:` cell; `$1374.60` is gone. The text layer has it.
3. **The check:** collect every decimal amount from the text layer, collect every number from the parsed text, and report text-layer amounts the parsed text lacks. Amounts are compared as `Decimal`s, so `$1,813.00` and `1813.0` count as the same value.
4. **Extraction behaved correctly on 11077:** it read all 25 lines and set `total` to `None` instead of inventing one, as the prompt demands. The lines add up to exactly 1374.60, the dropped total. So the line data is right and only the total is missing.
5. **Why not just copy the total from the text layer?** Because that would make the text layer a second source of truth that nothing checks. The design treats this as a *signal*: the case is held and the agent (Phase 7) investigates, citing both reads as evidence. The cross-check is a check on Nemotron, not a replacement for it.
6. **Limits:** a scanned PDF has no text layer, so the check returns `None` (skipped), not "all fine". And the check only looks at numbers, the values money depends on.

**The bug in my first version:** looking only for `$` amounts silently checked nothing on receipts and POs, while still printing "all found". A check that can pass by seeing nothing is worse than no check, so the output now always prints how many amounts it compared.

**Why it matters next:** Phase 1 is complete: three PDFs in, three validated `Document`s out, with a read-error check. Phase 2 compares them.
