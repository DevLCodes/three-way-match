# Step 03.1: Local Supabase Postgres

**Goal:** run the same database stack locally that production will use, so the state machine, queue, cron and vectors can be built and watched on your Mac.

## Files

| File | What it is |
|---|---|
| [`supabase/config.toml`](../../supabase/config.toml) | Local stack settings from `supabase init`: Postgres 17, database on port 54322, Studio (web UI) on 54323 |
| [`scripts/db_info.py`](../../scripts/db_info.py) | Connects and prints the Postgres version and the four extensions this project needs |
| [`pyproject.toml`](../../pyproject.toml) | Adds `psycopg`, the Postgres driver for Python |

## What happened

1. **The Supabase CLI** runs a full copy of a Supabase project in Docker: 12 containers. The one that matters most now is `supabase_db_three-way-match`, Postgres 17.11. The others are what a cloud project also has: `auth` (sign-in, used for approvers in Phase 8), `storage` (files), `rest` (an automatic API), `studio` (a web UI to look at tables), `kong` (the gateway in front of them), and logging.
2. **Why the full stack instead of plain Postgres:** production runs on Supabase, so building against the same image means pg_cron, pg_net, Vault and Auth behave the same locally and in the cloud. The first start downloads every image (9.5 minutes); later starts take seconds.
3. **`scripts/db_info.py`** connected with `psycopg` using the `DB_URL` (user `postgres`, password `postgres`, port 54322; local-only defaults) and asked Postgres two questions: its version, and which extensions are *available*.
4. **Extensions** add features to Postgres. All four are available but none is installed yet; the migrations in step 03.2 onward switch them on:
   - **pgmq** keeps a job queue inside Postgres, so a state change and its next job can be saved in one transaction (step 03.4).
   - **pg_cron** runs SQL on a schedule, like a cron job (the drain trigger).
   - **pg_net** lets that SQL make an HTTP call (to wake the worker on Cloud Run).
   - **vector** (pgvector) stores embeddings for the agent's memory (Phase 7).
5. **0 tables in `public`:** an empty database, ready for the first migration.

You can browse the database in Studio at http://127.0.0.1:54323. Stop the stack with `supabase stop`; data is kept between restarts.

**Note:** the old repo's Docker containers (`applied-ai-engineer-db-1` on port 54329, `applied-ai-engineer-api-1` on 8080) are still running from before. They don't conflict with this stack.

**Why it matters next:** step 03.2 creates the first tables, `cases` and `case_events`, and makes `case_events` impossible to edit.
